# Deploying Pinpoint

The app is three pieces, and they want three different hosts:

| Piece | Host | Why |
|---|---|---|
| `apps/web` (Vite + React) | **Vercel** | Static build. Perfect fit. |
| `apps/api` (Express + Prisma + Socket.IO + BullMQ) | **Render** (or Railway/Fly) | Needs a long-running process, WebSockets, and a queue worker. |
| PostgreSQL | **Neon** (free) | Serverless-friendly, works from anywhere. |
| Redis | **Upstash** (free) | Required by the socket adapter and BullMQ. |

**The API cannot go on Vercel.** Not a preference — Vercel's serverless functions have no long-lived process, so Socket.IO won't work, the BullMQ worker can't run, and `/ready` checks Redis on every call. Deploying the API there gives you a backend that answers `/health` and fails everything else.

## Corrections to the guide you were following

That guide targets the **legacy** `server/` and `client/` trees, which are kept only as a reference during the staged migration. Following it deploys the superseded app.

| The guide says | What is actually true |
|---|---|
| Root Directory: `server` | Root Directory must be the **repo root**. The API is `apps/api`, and it imports `@pinpoint/shared`, so the build needs the whole workspace. |
| Root Directory: `client` | The web app is `apps/web`. Root Directory stays the repo root; `vercel.json` sets the build command and output dir. |
| `cd server && npx prisma db push` | Schema lives in `apps/api/prisma`. Use `migrate deploy`, not `db push` — the repo has committed migrations, and `db push` skips them. |
| `CLIENT_URL=*` | The variable is `WEB_ORIGIN`, and it must be a real URL. `apps/api/src/config.ts` validates it with `z.url()`, so `*` makes the API refuse to boot. |
| `GEMINI_MODEL=gemini-3.5-flash-lite` | Keep the default `gemini-2.0-flash` unless you have verified that model ID exists on your key. |
| `GEMINI_API_KEY=AQ.Ab8RN6...` | AI Studio keys start with `AIza`. An `AQ.` value is an OAuth token, not an API key, and it will 401. |

## 1. Database — Neon

1. Create a project at neon.tech, copy the **direct** (non-pooled) connection string. It looks like:
   `postgresql://user:pass@ep-xyz.region.aws.neon.tech/neondb?sslmode=require`
2. From your machine, create the tables and demo data **before** deploying anything:

```bash
cd /home/jeevan/Projects/Stark_learning
export DATABASE_URL="postgresql://...neon.tech/neondb?sslmode=require"

npm run db:generate
npm run db:migrate      # prisma migrate deploy — applies prisma/migrations
npm run db:seed         # demo user + sample topic/palace
```

Use the direct string, not the pooled one: migrations need a direct connection. At hackathon scale the app can use it too.

## 2. Redis — Upstash

Create a free Redis database, copy the connection string. It starts with `rediss://` (TLS). Both the Socket.IO adapter and BullMQ accept it as-is.

## 3. API — Render

The repo ships `render.yaml`, so:

1. Render dashboard -> **New -> Blueprint** -> pick `pauljoe2k/Stark_learning`. It reads `render.yaml` and creates both services.
2. Fill the `sync: false` secrets:

| Key | Value |
|---|---|
| `DATABASE_URL` | Neon direct string |
| `REDIS_URL` | Upstash `rediss://...` |
| `WEB_ORIGIN` | your Vercel URL (set it in step 5; a placeholder is fine for now) |
| `API_PUBLIC_URL` | `https://pinpoint-api.onrender.com` (this service's own URL) |
| `GEMINI_API_KEY` | a fresh `AIza...` key |
| `DEMO_PASSWORD` | `PinpointDemo123!` |

`JWT_SECRET` is generated by the blueprint. `PORT` is injected by Render — don't set it.

Prefer clicking? New -> **Web Service** -> same repo -> Runtime **Docker** -> Dockerfile path `apps/api/Dockerfile` -> Docker build context `.` -> health check `/health`.

## 4. Web — Vercel

The repo ships `vercel.json`, which sets the monorepo build for you.

1. Vercel -> **Add New -> Project** -> import the repo.
2. Leave **Root Directory** at the repo root. Do not pick `apps/web`.
3. Add one environment variable: `VITE_API_URL` = your Render URL, no trailing slash.
4. Deploy. Vercel runs `npm run build --workspace @pinpoint/web` and serves `apps/web/dist`.

`VITE_API_URL` is baked in at build time — if you change it later you must **redeploy** the frontend, not just save the variable.

## 5. Wire the two together

Set `WEB_ORIGIN` on Render to the exact Vercel URL (`https://stark-learning-web.vercel.app`, no trailing slash) and let the API redeploy. CORS allows one origin; a mismatch shows up as a CORS error on every request in the browser console.

## 6. Smoke test, in this order

```bash
curl https://pinpoint-api.onrender.com/health   # {"status":"ok"}
curl https://pinpoint-api.onrender.com/ready    # database + redis healthy
```

Then in the browser: log in with the seeded demo account, create a topic, upload a 1-page PDF, run an Explain, open the Palace.

## Free-tier realities

- **Render free sleeps after ~15 minutes idle** and takes 30-60s to wake. The PRD already lists this as a demo risk: hit `/health` a minute before you present, or pay for the cheapest always-on instance.
- **Background workers are not on Render's free plan.** The blueprint asks for `starter`. If you won't pay, run the worker on your laptop during the demo against the same Neon + Upstash: `npm run worker --workspace @pinpoint/api`. Extraction jobs then still process — they just need your laptop awake.
- **Uploads are ephemeral.** `STORAGE_PROVIDER=local` writes into the container, which is wiped on every deploy and restart. Fine for a demo where you upload live; set `STORAGE_PROVIDER=cloudinary` plus the three `CLOUDINARY_*` variables if you need files to survive.
- **Neon free** suspends an idle database; the first query after a pause takes a second or two.

## Rollback

Both hosts deploy per-commit. In Render: **Deploys -> pick the previous one -> Redeploy**. In Vercel: **Deployments -> ... -> Promote to Production**.
